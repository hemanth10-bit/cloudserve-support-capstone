# Governance (B-18) - 2026-11-11

What must be true before this system could speak to a real customer. Filled copy of the Governance Framework:
`Capstone_Pack/03_Reference/Governance_Framework_FILLED.docx`. Likelihood and impact are the author's judgement from the measurements
cited, to be reviewed. The person named as owner is the sole author of this individual project.

## 1. Decision logging
Every ticket gets a classification row and a routing row; drafted replies add generation and validation rows. Fields follow the
Governance Framework minimum record plus the router rule and requirement ids (`src/decision_log.py`, D-09). Coverage check:
the log reconciles per ticket and stage (validation run: 276 expected, 276 logged, 0 missing; reconcile never raises and reports
gaps). The log never stores the customer's name or id, only a hash and a short excerpt (tested).

## 2. Risk register
| ID | Risk | Likelihood | Impact | Mitigation in the design, and what is still open | Owner |
|---|---|---|---|---|---|
| R-01 | The system answers confidently and incorrectly | High | High | Seven-check validator on every reply (citations resolve to retrieved passages; no promises, billing, data-location or unsupported figures; claim-support check that fails closed). Always-escalate classes (security, compliance, feature, unclear) are enforced in router code outside any model. Measured limit: on 216 development tickets 29 of 33 label-defined unanswerable tickets still got a reply, and 74.6% of replies sent were for tickets the labels call answerable. Human review (D-19, one assessor, 60 replies that had passed the validator): 0 unsupported claims (95% upper bound 6.0%); 11 replies lacked the citation in their text, now fixed. The framework asks for two assessors, so a second review is still outstanding. Not deployable on automatic sending until that and a shadow-mode trial are done (see declaration). | Hemanth Kumar P (author and operator) |
| R-02 | Private data appears in an outbound response | Low | High | Validator private_data check blocks email, phone, key/token, card number, and the customer's own account id or full name (first-name greeting allowed); prompt rule forbids repeating personal data; blocked, never redacted-and-sent. The decision log stores a hash and a 120-character excerpt, never the customer's name or id (tested). 0 detections in 296 tickets processed. Residual gap: a name other than the customer's, or an address in prose, is not detected by pattern. | Hemanth Kumar P (author and operator) |
| R-03 | A customer's input is treated as an instruction | Medium | Medium | Delimiter tags in customer text are stripped in code, the ticket is wrapped in <ticket> tags, rules are repeated after it, and prompts say the text is data. The checks that matter (commitments, private data, prompt leakage, always-escalate) run in code on the output, so a successful injection still cannot send a promise or a leak. The system has no tools and no data access beyond retrieved documentation, so the worst outcome is bad text, which the validator inspects. Tested with delimiter-closing and refund-demanding tickets. | Hemanth Kumar P (author and operator) |
| R-04 | Some customer groups receive worse answers | Medium | Medium | Group fields (tier, region, fluency, channel) are not inputs to any decision (a test fails if one is read). Audit with intervals and tests (docs/fairness_audit.md): no gap between tier, region, fluency or channel is statistically supported; one gap is supported, long tickets get a right answer less often (62.7% vs 84.1%, p = 0.017, one of 29 comparisons so suggestive only). Not yet mitigated: candidate is escalating long multi-issue tickets; to be decided after the human review. | Hemanth Kumar P (author and operator) |
| R-05 | The documentation the system relies on goes stale | Medium | Medium | Every reply cites article ids, so a reviewer can trace a wrong answer to a stale article quickly, and the log records the sources used. No automatic staleness detection is built: all 29 articles show last_reviewed_days_ago = 0 in the data, so freshness cannot be tested. Proposed: monthly article review by the knowledge owner, and re-index (the index rebuilds when the corpus changes). | Hemanth Kumar P (author and operator) |
| R-06 | The model provider becomes unavailable | High | Low | Retries with backoff for transient errors, a circuit breaker (opens after 3 failed requests, 30 s cooldown), and a template hand-over note so every ticket still gets a logged escalation. Induced in tests (21 cases) and live: provider disconnected, 40 of 40 tickets escalated, run finished in 31 s, log reconciled. | Hemanth Kumar P (author and operator) |
| R-07 | Latency degrades under load | High | Medium | NOT MET. p95 17.9 s and median 5.9 s on the validation gate run against a 3 s target (free 8B model, two to three calls per ticket). Mitigations in place: response cache, circuit breaker so an outage does not multiply the delay. Not solved; recorded for the PRD revision. Chat customers are the group most hurt. | Hemanth Kumar P (author and operator) |
| R-08 | Costs rise unexpectedly with volume | Low | Low | Free-tier model and open-source components only; no paid key configured; responses cached. Gap: nothing caps spend if someone later switches to a paid model; a budget limit would be needed first. | Hemanth Kumar P (author and operator) |
| R-09 | Reported results overstate quality because the labels are noisy and the hallucination rate rests on one assessor and 60 replies | High | Medium | Validation and development results are reported separately; seen-text overlap is stated (62 of 80 validation tickets share text with development); out-of-fold figures are quoted for the classifier; the same-model judge was run, found unusable and discarded (D-14); the report states what is unmeasured. | Hemanth Kumar P (author and operator) |
| R-10 | The routing threshold is wrong for real traffic | High | Medium | The 0.64 threshold assumed a 20% pass-through; measured 88% (29 of 33) on development and 73% on validation. Re-fitting would give 0.87-0.90 and automate only 5-17% of tickets. Not changed: the author decided on 2026-11-12 to keep 0.64 because the evidence on whether the passed tickets are actually wrong is missing (D-13, D-14, D-17). Shadow mode before any live sending. | Hemanth Kumar P (author and operator) |
| R-11 | A secret (the model API key) leaks through code, history or the submission | Low | High | Key is only in a git-ignored .env; never pasted in chat; .env.example holds a placeholder. Scan of files and git history done 2026-11-14: 0 hits for the real key and for common key patterns (D-20); to be repeated on the final zip. | Hemanth Kumar P (author and operator) |
| R-12 | The kill switch is left on, or cannot be reached when needed | Low | Medium | Kill switch fails closed (an unreadable flag counts as on). `python -m src.killswitch status` shows the state and the reason, and every escalation under it carries rule KS and the reason in the log so a forgotten switch is visible in the metrics. Anyone who can write to storage/ can operate it; access to that directory is the control. | Hemanth Kumar P (author and operator) |

## 4. Guardrails
| Guardrail | What it checks | What happens when it fires | Status |
|---|---|---|---|
| Private data | Names, addresses, keys, account numbers, anything identifying another customer. | Block and escalate. Never redact and send. | Implemented: validator private_data check (email, phone, key, card, customer id or full name). Tested with a red-team set. Reply is withheld and the ticket escalated. |
| Grounding | Every factual claim traceable to a retrieved passage. | Block and escalate with the unsupported claim flagged. | Implemented: citation check in code plus a claim-support check that fails closed; a code check also blocks figures not in the sources. Unsupported claim is recorded in the log. Weakness: same small model checks the claims (D-11). |
| Instruction integrity | The ticket content has not altered the system's instructions. | Block, escalate and record the input for review. | Partly: tags in customer text are stripped, prompt_leak check blocks replies containing our instructions, the always-escalate rule is in code. The input excerpt and hash are in the log for review. Not detected: an injection that changes tone without any of the blocked patterns. |
| Tone and scope | Stays within support scope; makes no commitments. | Block. Commitments about refunds or timelines are not the system's to make. | Implemented: commitment, billing and data-location checks. Any reply promising a refund, credit, date, roadmap item or compliance status the sources do not state is blocked. |
| Confidence floor | The routing threshold was actually applied. | Escalate. A missing confidence score is not a high one. | Implemented: the router applies its threshold and rules to every ticket and a missing score gives answerability 0, so the ticket is escalated. Unit tested. The threshold itself is under review (R-10). |

## 5. Incident response
| Step | What to do | Who does it | How long it should take |
|---|---|---|---|
| 1. Detect | Any of: a customer or agent reports a wrong, risky or leaked reply; the daily metrics report shows blocked replies or guardrail activations rising; the decision log shows tickets answered that should have been escalated; the provider fails. Daily check: python -m evaluation.harness metrics file and `python -m src.killswitch status`. | Whoever notices tells the operator; the operator reviews the metrics daily while the system is live. | Report to operator within 15 minutes of noticing. |
| 2. Contain | If a wrong or harmful reply could still be sent: run `python -m src.killswitch on "reason"` (creates storage/KILL_SWITCH). From the next ticket every ticket is escalated to a person and no model is called; replies already drafted are held back at the last gate. Then check `python -m src.killswitch status`. | Operator, or anyone with write access to the deployment's storage/ directory. | Under 5 minutes; takes effect on the next ticket. |
| 3. Assess | Find the affected tickets: query decisions.db for the ticket ids, stage, prompt_version, guardrail_results and sources_used; read the reply and the cited article. Decide the cause: wrong article, stale article, model error, validator miss, or an input that manipulated the reply. Count how many replies went out and to whom. | Operator, with the support lead for the customer-facing view. | Within 2 hours. |
| 4. Notify | Tell the head of support and the affected customers' account owners which replies were wrong and what the correct answer is. If personal data left the system, notify the data owner at once and follow the client's breach procedure. Record what was said and when. | Operator to head of support; head of support to customers. | Support lead within 1 hour of confirming; private data immediately; customers the same day. |
| 5. Remediate | Send corrected replies to affected customers. Fix the cause: correct or re-review the article, add the failing example to tests/test_validator.py (red-team set) or tighten a check, change the prompt as a new version (never overwrite). Re-run the test suite and the development metrics before lifting the switch with `python -m src.killswitch off`. | Operator. | Corrections same day; fix and re-test within 2 working days. |
| 6. Review | Write a short incident note: timeline, cause, how it was detected, what the log showed, what changed. Check whether the same path could produce other wrong replies (query the log for similar tickets). Update the risk register and PRD revision log. | Operator and support lead. | Within 5 working days. |

Times are proposed, for the client to confirm.

### The kill switch
| Question | Answer |
|---|---|
| What is the mechanism? | A flag file (storage/KILL_SWITCH, created by `python -m src.killswitch on "reason"`) or the environment variable AUTO_RESPOND_DISABLED=1. Checked for every ticket and again immediately before a drafted reply would be released. If the check cannot run, the system acts as if it were on. |
| Who is authorised to use it? | The operator (Hemanth Kumar P) and any named on-call person with write access to the deployment's storage/ directory. Access to that directory is the control; the flag file records the reason and time. |
| How long until it takes effect? | The next ticket: the check is a file-existence test, measured under 1 ms. No restart or deployment is needed for the flag file (the environment variable needs a process restart, so use the file). |
| What happens to tickets in flight? | A ticket not yet routed is escalated with rule KS. A ticket already drafted or validated is held back at the last gate before release and escalated with a note. No model is called while the switch is on, so hand-over notes are templates. Nothing is dropped; every ticket still gets a logged escalation. |
| How is it tested? | tests/test_killswitch.py (9 tests): file and environment variable, no model calls, takes effect on the next ticket and lifts cleanly, in-flight hold-back, logged with rule KS, fails closed when unreadable, command line. Live check: harness on 20 validation tickets with the switch on gave 20 of 20 escalated, 0 drafted replies. |

## 6. The declaration
| Statement | Position |
|---|---|
| This system must never ... | send a promise it cannot keep (a refund, credit, date, roadmap item or compliance status), send a customer's or anyone's private data, or answer a security incident, compliance, feature or unclear request automatically. |
| The mechanism that enforces that is ... | Router rule R2 (always-escalate classes, in code, outside any model; 0 of 14 such validation tickets and 0 of 87 development ones answered), the validator's commitment, billing, data-location and private-data checks on every reply (red-team set blocks all 19 test cases), the decision log that records every decision (276 of 276 reconciled on the validation run), and the kill switch. |
| The most likely way it could still cause harm is ... | a fluent, correctly cited but wrong or out-of-date answer to an ordinary ticket that passes every check. On development data 29 of 33 label-defined unanswerable tickets that were auto-routed still got a reply, the validator stopped only 4, and the one-assessor review of 60 passed replies found no unsupported claims (upper bound 6%), which is too small a sample to rule this out. Long multi-issue tickets look most exposed (62.7% right vs 84.1% for short ones). |
| We would not deploy this without first ... | repeating the hallucination review with a second assessor (the first found 0 of 60; upper bound 6%, above the 5% target); deciding the routing threshold from evidence that the passed tickets are actually fine; running in shadow mode (drafts shown to agents, nothing sent) for a trial period; setting a latency target the system meets; and agreeing an article-review process with the knowledge owner. |
